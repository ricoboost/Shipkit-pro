# Structure du Projet

ShipKit suit une structure bien organisée basée sur les conventions de Next.js App Router.

## Vue d'Ensemble des Répertoires

```
shipkit/
├── content/
│   └── docs/           # Fichiers MDX de documentation
├── prisma/
│   └── schema.prisma   # Schéma de base de données
├── public/             # Ressources statiques
├── src/
│   ├── app/            # Pages Next.js App Router
│   ├── components/     # Composants React
│   ├── config/         # Fichiers de configuration
│   ├── hooks/          # Hooks React personnalisés
│   ├── lib/            # Bibliothèques principales et utilitaires
│   └── middleware.ts   # Middleware Next.js
├── .env.example        # Modèle de variables d'environnement
├── next.config.ts      # Configuration Next.js
└── package.json        # Dépendances
```

## Concepts Clés

### Groupes de Routes

Les groupes de routes `(groupName)` organisent les routes sans affecter l'URL :

- `(marketing)` - Pages publiques à `/`, `/pricing`, `/blog`
- `(auth)` - Pages d'authentification à `/login`, `/register`
- `(dashboard)` - Pages utilisateur à `/dashboard`, `/settings`
- `(admin)` - Pages admin à `/admin`

### Abstraction des Fournisseurs

Chaque fonctionnalité majeure utilise une interface unifiée :

```typescript
// lib/auth/index.ts exporte l'interface unifiée
export const auth = getAuthProvider(); // Retourne le fournisseur configuré

// L'utilisation est la même quel que soit le fournisseur
const session = await auth.getSession();
```

### Sécurité des Types

Toutes les API utilisent Zod pour la validation et oRPC pour les endpoints typés :

```typescript
// Appels API entièrement typés
const result = await rpc.users.getProfile.query();
```
